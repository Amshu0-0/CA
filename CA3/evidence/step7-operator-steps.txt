2. Scale replicas
====================================================================================================

A replica is a means, not a goal. The REST API has 2 pods so that it keeps answering while one of them is replaced (the goal 'api-gap' in slo.json).
To see the manual step, the REST API goes to 3 pods and then back. This is the only Deployment without an autoscaler.

   $ kubectl -n ca3 get deployment restapi
       now: 2 wanted, 2 ready (2 pods)
   ok:       the REST API starts with all its pods ready (2 of 2)
   $ kubectl -n ca3 scale deployment/restapi --replicas=3
       deployment.apps/restapi scaled
   ok:       kubectl scale to 3 was accepted
       after 8 s: 3 wanted, 3 ready (3 pods)
   ok:       the extra pod became ready within 240 s (3 of 3 ready)

   $ curl https://<node-address>:30080/stats      (with the login of the Secret restapi-login)
       HTTP 200   {"collection":"flows","database":"ca3","documents":370358}
   ok:       the REST API answers /stats with 3 pods

Back to the normal number. The file restapi/restapi.yaml says 2. A change made with  kubectl scale  is not in the file, and  kubectl apply -k .  does not undo it
(apply only sends what changed in the file), so it is undone by hand here. To keep a different number, change  replicas:  in the file.
   $ kubectl -n ca3 scale deployment/restapi --replicas=2
       deployment.apps/restapi scaled
       after 4 s: 2 wanted, 2 ready (2 pods listed)
   ok:       the REST API is back to 2 pods, all ready

The other two parts that have more than one pod are not scaled by hand: the processor (1 to 3 pods, processor/hpa.yaml) and the load generator (1 to 5, producer/load/hpa.yaml)
belong to their autoscalers. A  kubectl scale  on them is undone within about 15 seconds. To change how many they may have, change minReplicas / maxReplicas in the file
and run  kubectl apply -k .  The processor cannot use more than 3 pods: the Kafka topic has 3 partitions, and one partition is read by one processor at a time.

3. Check the certificates
====================================================================================================

A certificate is valid until a fixed date. The bootstrap Job makes them valid for 365 days (VALID_DAYS in processor/bootstrap.py).
The end dates are read from the Secrets; only the certificate part is looked at, no key is printed or saved.

When a date comes close, the certificates have to be replaced before it passes: a program with an expired certificate is refused by the others, and the pipeline stops.

====================================================================================================
4. Rotate a certificate: NOT DONE here, on purpose
====================================================================================================

With the design of this stack a certificate cannot be replaced while the data stays. Three reasons, all in processor/bootstrap.py:
  - The private key of the CA was never stored, so nobody can sign a new certificate that the old CA vouches for.
  - The Job bootstrap makes all 13 Secrets or none. When only some exist it stops with an error, because new certificates would not match the old ones.
  - The passwords are in the same 13 Secrets, and MongoDB created its users only once, when its disk was still empty (the official image runs its set-up
    scripts only for an empty data directory). A new password would not match the old disk.

So today the only way to new certificates is   make down   (deletes everything, also the disks) and   make up   (the Job makes everything new, the replay Job loads the sample flows again).
That is fine for a course project and wrong for a production system. runbook.md says what a production system does (cert-manager renews certificates before they end and the
programs reload them) and what would have to change in this stack: keep the CA key somewhere safe and separate (a tool such as cert-manager, or a Secret that only a renewal Job may read), and make the passwords separate from the certificates.
This step was not run, so nothing here claims that it works.
