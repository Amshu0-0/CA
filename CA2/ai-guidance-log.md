# AI guidance log (CA2)

*Started October 8, 2026 (Step 4). This is the raw material for the CA2 Integrity Packet.*

I used Claude (Anthropic) to design and write the manifests, the programs, the Terraform and the Ansible, and to test them. This log records each consequential piece of guidance: what the AI recommended, which official page backs it up, what was actually tested (and what was not), and what I decided after reading the source myself.

**How to fill a row.** Open the official link, find the sentence that supports or contradicts the recommendation, tick the box, and write one line of outcome (accepted, changed or rejected, and why). Nothing here counts as verified until I have done that myself.

## Decisions the AI recommended

| # | Decision and what the AI recommended | Official source to read | What was tested, and what was not | I verified, and my outcome |
|---|---|---|---|---|
| 1 | **Kafka and MongoDB as StatefulSets with their own disks.** A broker and a database need a stable name and storage; a Deployment gives neither. | [StatefulSets](https://kubernetes.io/docs/concepts/workloads/controllers/statefulset/) | Schema-valid (`make validate`). The checker confirms each `serviceName` is a headless Service. Not tested yet: data surviving a pod restart (Step 6). | ☐ |
| 2 | **Two Services per StatefulSet: headless plus ClusterIP.** The headless one gives pods their DNS names; the ClusterIP one is the stable address for clients. | [Headless Services](https://kubernetes.io/docs/concepts/services-networking/service/#headless-services) | The checker confirms every selector and named port matches a real pod. | ☐ |
| 3 | **`enableServiceLinks: false` on Kafka.** Kubernetes injects `KAFKA_PORT`-style variables because a Service named `kafka` exists, and the Confluent image reads `KAFKA_*` variables as configuration. | [Service: environment variables](https://kubernetes.io/docs/concepts/services-networking/service/#environment-variables) | The injection mechanism is documented. **Not confirmed:** that this image really fails without the flag. Test in Step 5: remove the flag and read `kubectl logs kafka-0`. | ☐ |
| 4 | **MongoDB credentials through `MONGO_INITDB_ROOT_*_FILE`.** The official image can read its admin user and password from mounted files. | [Docker Hub: mongo, "Docker Secrets"](https://hub.docker.com/_/mongo) | The checker confirms the `_FILE` variables and the Secret mount exist. Not tested yet: MongoDB starting with them (Step 5). | ☐ |
| 5 | **Secrets mounted as files, with `defaultMode` written in decimal (256, 288).** Meets "mount secrets, do not embed them". Decimal avoids a YAML octal trap. | [Secrets](https://kubernetes.io/docs/concepts/configuration/secret/), [Volumes: secret](https://kubernetes.io/docs/concepts/storage/volumes/#secret) | The checker finds no literal secret in any manifest. The octal reasoning is unverified. | ☐ |
| 6 | **`runAsNonRoot: true` needs a numeric `USER` in the image.** Kubernetes cannot prove that a user *name* is not root. | [Security context](https://kubernetes.io/docs/tasks/configure-pod-container/security-context/) | The checker reads each Dockerfile for `USER 1000`. | ☐ |
| 7 | **Init containers instead of `depends_on`.** Kubernetes has no `depends_on`; an init container waits until Kafka or MongoDB accepts connections. | [Init containers](https://kubernetes.io/docs/concepts/workloads/pods/init-containers/) | Schema-valid. | 8 | **NetworkPolicy: default-deny plus one allow per connection, plus DNS.** | [Network Policies](https://kubernetes.io/docs/concepts/services-networking/network-policies/) | The checker confirms every policy selector matches a real pod. **Not tested:** enforcement. That is Step 6 on k3s. | ☐ |
| 9 | **RBAC: no API token in pods, and no `secrets` permission anywhere.** | [RBAC](https://kubernetes.io/docs/reference/access-authn-authz/rbac/), [Service accounts](https://kubernetes.io/docs/tasks/configure-pod-container/configure-service-account/) | The checker confirms no Role can read Secrets and every binding resolves. `make rbac-check` runs on the cluster in Step 6. | ☐ |
| 10 | **HPA rules:** no `replicas` on autoscaled Deployments, CPU requests required, metrics-server needed, processor maximum 3 (one consumer per partition). | [Horizontal Pod Autoscaling](https://kubernetes.io/docs/tasks/run-application/horizontal-pod-autoscale/) | The checker enforces the first two. The scaling test is Step 7. | ☐ |
| 11 | **Images built by GitHub Actions and pushed to ghcr.io.** There is no Docker on the laptop, and the workflow's own token logs in, so no password is stored. | [Working with the Container registry](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry) | The Actions run finished green and the packages are public (Step 2). | ☐ |
| 12 | **Pod Security Admission `baseline` on the namespace.** | [Pod Security Admission](https://kubernetes.io/docs/concepts/security/pod-security-admission/) | Schema-valid. Pods being admitted is tested in Step 5. | ☐ |
| 13 | **`persistentVolumeClaimRetentionPolicy: whenDeleted: Delete`.** Deleting a StatefulSet also deletes its disks, for a clean teardown. | [StatefulSets: PVC retention](https://kubernetes.io/docs/concepts/workloads/controllers/statefulset/#persistentvolumeclaim-retention) | Schema-valid. The disks really disappearing is checked in Steps 5 and 8. | ☐ |
| 14 | **k3s instead of kubeadm, minikube or EKS.** One small binary that already includes DNS, metrics-server, local-path storage and a NetworkPolicy controller, so the course features work on three small machines. | [K3s requirements](https://docs.k3s.io/installation/requirements) | A real k3s v1.37.1 server started with the exact config the playbook writes, and CoreDNS, metrics-server and local-path-provisioner came up. **Not tested before the cluster build:** agents joining the server. | ☐ |
| 15 | **A pinned installer: k3s version plus the installer's SHA-256 checksum.** A changed or tampered script stops the run. | [K3s environment variables](https://docs.k3s.io/reference/env-variables), [ansible.builtin.get_url](https://docs.ansible.com/ansible/latest/collections/ansible/builtin/get_url_module.html) | The checksum matches the installer at the pinned release tag. | 16 | **Traefik and servicelb switched off.** The REST API is published by a NodePort, so neither is needed, and leaving them out means nothing listens on ports 80 and 443. | [K3s packaged components](https://docs.k3s.io/installation/packaged-components) | On a real k3s v1.37.1 server, `kube-system` held only coredns, local-path-provisioner and metrics-server. | ☐ |
| 17 | **Kubernetes Secrets encrypted at rest** (`secrets-encryption: true`). | [K3s secrets encryption](https://docs.k3s.io/cli/secrets-encrypt) | On a real k3s server I stored a Secret and read the raw database entry: it carried the `k8s:enc:aescbc:v1` prefix and the plaintext was not in it. | ☐ |
| 18 | **The firewall:** three rules from one IP address (SSH 22, Kubernetes API 6443, REST 30080), four rules between the nodes only (6443, 10250, 8472/udp, ping), nothing else inbound. | [K3s requirements: inbound rules](https://docs.k3s.io/installation/requirements), [Security groups](https://docs.aws.amazon.com/vpc/latest/userguide/vpc-security-groups.html) | An offline plan (19 resources) and a full apply and destroy against an AWS emulator. | 19 | **Encrypted disks and IMDSv2 only** (a program on the machine needs a token to read its metadata). | [Instance metadata service](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/configuring-instance-metadata-service.html) | Plan only. | ☐ |
| 20 | **`ignore_changes = [ami]`** with a "newest Ubuntu 24.04" lookup, so a newer image never replaces a running machine. | [Terraform lifecycle](https://developer.hashicorp.com/terraform/language/meta-arguments/lifecycle) | In the emulator test no plan proposed replacing a machine. **Not tested:** a newer image appearing later. | ☐ |
| 21 | **My IP address looked up on every run** (`admin_cidr: auto`), not typed into the code. | [http data source](https://registry.terraform.io/providers/hashicorp/http/latest/docs/data-sources/http) | Tested against a stand-in for the lookup service, including an address change. | ☐ |
| 22 | **Ansible written to be repeatable:** each task checks first, and a changed config applies immediately. | [Idempotency](https://docs.ansible.com/ansible/latest/reference_appendices/glossary.html#term-Idempotency), [Handlers](https://docs.ansible.com/ansible/latest/playbook_guide/playbooks_handlers.html) | `ansible-lint` passes at its strictest profile. ## Where the AI was wrong, found by testing

| # | The AI's mistake | How it was found | Correction |
|---|---|---|---|
| A | The three init containers were written with no CPU or memory limits. | The checker, run on the pushed repository, gave 3 warnings. | Limits added in Step 3. |
| B | The checker called the DNS policy's selector for CoreDNS "matches no pod", although it points at another namespace. | Running the checker on the finished tree. | The checker now skips a selector that sits next to a `namespaceSelector`. |
| C | `make down` hid teardown errors because of a leading `-` in the Makefile. | Reading the target while testing teardown against a real API server. | The `-` was removed. |
| D | The availability-zone lookup always ran, so a plan with no AWS access failed with "fetching Availability Zones". | An offline plan. | The lookup is skipped when `availability_zone` is set in `config.yml`. |
| E | The checker's `.gitignore` rule matched substrings, so deleting the `*.tfstate` line went unnoticed (the `*.tfstate.*` line still contained `.tfstate`). | Deliberately breaking the cluster files to see whether the checker noticed. | It now requires exact lines. All 11 deliberate breakages are caught. |
| F | Terraform printed colour codes even when its output was piped, so saved evidence would have been full of `[32m` characters and the `grep` for `Plan:` found nothing. | Running the exact evidence commands against an offline AWS emulator. | `TF_CLI_ARGS ?= -no-color` in the Makefile. |
